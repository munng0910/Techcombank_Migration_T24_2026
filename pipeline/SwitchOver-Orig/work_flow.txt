# GoldenGate startup: follow the DBA Jenkins workflow

Pipeline: jenkins/Jenkinsfile_run_start_service.groovy
Reference: jenkins/Jenkinsfile_t24_dba_new.groovy
Remote script: start_ogg_services.sh, already deployed on the DC and DR nodes

The pipeline defines its configuration first, creates an Ansible pod, writes the
playbook inside that pod, and executes it. There is no checked-in playbook or
separate Jenkins inventory-planning framework required for this job.


# 1. Define all environment/site information before creating the pod

The top of the Jenkinsfile defines:
  - Production/development node classification, Vault URL, and AppRole credential ID.
  - SYSTEM_NAME and the filename of the playbook generated in the pod.
  - SITES: DC/DR inventory group, deployed script path, and Vault password key.

Resolve environment from JENKINS_URL using the reference pipeline's branching:
  Production Jenkins -> ENV=prod; clusters corelive1a/corelive1b; production Vault.
  Other Jenkins      -> ENV=dev; clusters pt/sit/techupgrade; development Vault.

Initialize the ENVIRONMENT and TARGET_SITE job parameters, then define:
  ENVIRONMENT        = the selected cluster
  TARGET_SITE        = DC or DR
  VAULT_PATH_OGG     = kv2/ogg/<ENVIRONMENT>/secret
  ANSIBLE_INVENTORY  = <prod|dev>/<ENVIRONMENT>.ini
  configuration     = Vault URL, AppRole credential ID, KV engine version 2
  ctx               = environment, site, target group, script path, selected Vault
                      key, inventory path, and generated playbook filename

The selected key is known before pod creation. Its secret list is built inside
the pod using buildOggSecrets/checkVaultExists, following the reference helper
pattern, after input/inventory validation and before the execution withVault.

All these settings and helper functions exist BEFORE podTemplate is called.
Hosts/IPs and SSH user are not duplicated in Jenkins; Ansible reads them from:
  inventory/database/t24/<prod|dev>/<ENVIRONMENT>.ini

Site and Vault-key mappings:
  DC / node 1 -> ogg_DC -> oggnode1_ansible_password
  DR / node 2 -> ogg_DR -> oggnode2_ansible_password

Only the selected node's key is probed/read from kv2/ogg/<ENVIRONMENT>/secret.
checkVaultExists checks availability with a scoped TEST_VAULT binding; the helper
then builds the selected key's PASS_OGG binding. An unavailable selected key stops
the job, never falls back to the other node, and does not require the other key.
Check the Vault key/path/permissions if the probe fails. Abort/interrupt requests
are propagated, not silently treated as a missing key.

The inventory variable ogg_ansible_password remains a common alias for the one
selected password; it is not the name of either node-specific Vault field.


# 2. Create the Ansible pod and run the reference workflow

Define configuration and helpers in Jenkins
  -> podTemplate(inheritFrom: 'ansible')
  -> node(POD_LABEL)
  -> ansiColor('xterm')
  -> Checkout SCM: cleanWs(), checkout scm
  -> Validate selected environment/site, deployed script path, and inventory file
  -> buildOggSecrets: checkVaultExists for the selected node's Vault key
  -> withVault(configuration, secrets): inject the selected password as PASS_OGG
  -> Confirm the selected operation once, as in the DBA pipeline
  -> runPlaybook(ctx)
       -> container('ansible')
       -> Write start_ogg_services.yml inside the pod
       -> Write temp_vars.yml containing environment lookups, not password values
       -> Execute ansible-playbook using the real inventory and selected site
       -> Remove both generated files in finally

ONNODE retains the reference's prod/dev classification. Actual execution is on
node(POD_LABEL) from the inherited Ansible pod, not node(ONNODE).

The first build may only initialize job parameters. Missing/invalid selections
stop before Vault lookup or service execution; rerun with valid parameter values.


# 3. Playbook generated inside the pod

The generated YAML contains two plays:

1. Pod-local inventory validation (hosts: localhost, connection: local):
   - Reject check mode and invalid startup inputs.
   - Require ogg_DC or ogg_DR to exist and resolve to exactly one host.
   - Require the selected host to declare SSH user localpwm.
   - Stop the playbook on validation failure before remote tasks.

2. Selected-site execution (hosts: the chosen ogg_DC or ogg_DR group):
   - Use the inventory's host address, SSH port, user, and SSH options.
   - sudo become oracle with flags -H -S -i.
   - Verify id -un returns oracle before executing the startup script.
   - Run /bin/bash -- <deployed-start_ogg_services.sh-path>.
   - Report stdout/stderr and preserve nonzero-exit failure behavior.

The invocation is equivalent to:
  ansible-playbook -i <canonical-inventory> -e @temp_vars.yml \
    --limit "<selected-OGG-group>,localhost" start_ogg_services.yml

localhost is the pod-local validation play only; it is not another remote site.
The remote play targets only the selected OGG group, never db_t24live/database
hosts or the unselected site. Missing/empty groups fail instead of silently
reporting a successful startup with no matched hosts.


# 4. Credentials and prerequisites

PASS_OGG is scoped by withVault:
  DC: oggnode1_ansible_password -> PASS_OGG
  DR: oggnode2_ansible_password -> PASS_OGG

The generated variables file still contains only lookup expressions:
  ogg_ansible_password    <- lookup('env', 'PASS_OGG')
  ansible_become_password <- ogg_ansible_password

The inventory uses ansible_password="{{ ogg_ansible_password }}" for localpwm SSH.
If sudo prompts, the same localpwm password is supplied; NOPASSWD also works.
No separate oracle password or GoldenGate application password is fetched.
The Bash script's own application configuration remains unchanged.

Before running:
  - Replace the DC/DR scriptPath placeholders in SITES with the deployed paths.
  - Ensure the Jenkins SCM checkout contains the canonical inventory and the
    ogg_DC/ogg_DR groups with ansible_user=localpwm.
  - Ensure the existing ansible pod template/container, Active Choices, Vault,
    workspace cleanup, and ANSI color support used by the reference are available.
  - Targets need Bash, sudo, Python compatible with Ansible modules, and permission
    for localpwm to run Ansible commands as oracle. A sudoers rule allowing only
    the literal command sudo su - oracle may require different configuration.

No controller allowlist, managed known_hosts credential, custom approver group,
shared-lock setup, or new timeout configuration is required by this version.
SSH host-key policy is inherited from inventory, like the reference. The local
sample disables host-key checking; this version does not claim to harden that
policy. Trusted host verification remains an infrastructure/security decision.

The startup script stops existing services before starting them. The administrator
must choose the correct target and handle any opposite-site shutdown/fencing.
disableConcurrentBuilds() protects this job only; there is no cross-job lock,
automatic failover/fencing, or automatic retry after an execution failure.

Neither start_ogg_services.sh nor orig/OGG_Failover_TCB-PT-orig.sh is modified.


# 5. Offline checks

From the workspace root, with Groovy and Python/PyYAML/Jinja2 available:
  groovy tests/ogg/validate_start_service.groovy
  python -I tests/ogg/test_start_ogg_contract.py -v

These verify the configuration -> pod -> checkout -> Vault -> confirmation ->
playbook generation -> execution order using mocks, plus generated YAML/Jinja
behavior. They do not create real pods, fetch credentials, send approvals, connect
to VMs, or run services. Full Jenkins/Ansible runtime validation remains separate.
